# ข้อตกลงระบบสมาชิกและ Admin CMS

วันที่บันทึก: 10 พฤศจิกายน 2026

สถานะ: สรุปจากการวางแผนร่วมกับเจ้าของโปรเจกต์ ยังไม่ได้เริ่มพัฒนาระบบสมาชิกหรือ CMS
ข้อกำหนดในเอกสารนี้เป็นการตัดสินใจของเจ้าของโปรเจกต์ระหว่างวางแผน ไม่ใช่ RQM เพิ่มเติมที่ได้รับจากลูกค้า

แบบเสนอฐานข้อมูลสมาชิก ขั้นตอนอนุมัติ และ RLS อยู่ใน [MEMBER_ACCESS_DESIGN.md](MEMBER_ACCESS_DESIGN.md) ยังไม่ได้ apply กับฐานข้อมูลจริง

## 1. เป้าหมายและขอบเขตล่าสุด

- ระบบจริงเป็น Web App ที่ใช้งานออนไลน์ทั้งหมด ไม่พัฒนาการใช้งานออฟไลน์ในขอบเขตนี้
- ผู้ใช้งานหลักคืออาจารย์ ใช้ Education และ Simulator เป็นสื่อประกอบการสอน
- ระยะแรกมีบทบาทอาจารย์และ Admin ไม่แยกบทบาทนักศึกษา
- อาจารย์ที่ผ่านอนุมัติเข้าถึงทุกหมวดได้ ไม่กำหนดสิทธิ์แยกตามหมวด
- HTML ไฟล์เดียวที่ export ไว้เป็น Demo สำหรับส่งตรวจงาน ไม่ใช่ระบบสมาชิกหรือ CMS production
- หากเอกสารแผนเดิมระบุว่าต้องรองรับ offline หรือ Supabase เป็นเพียงงานในอนาคต ให้ใช้ขอบเขตออนไลน์และสมาชิกในเอกสารนี้สำหรับงานระยะถัดไป
- เอกสาร handoff จากลูกค้าเก็บเป็นหลักฐานเดิม ไม่แก้ข้อความต้นฉบับให้เป็นข้อตกลงใหม่

## 2. การสมัครและข้อมูลสมาชิก

ทุกคนสมัครได้ แต่ต้องยืนยันอีเมลและผ่านการอนุมัติจาก Admin ก่อนเข้าถึง Education

| ข้อมูล | ข้อตกลง |
|---|---|
| ชื่อ–นามสกุล | บังคับกรอก |
| อีเมล | บังคับกรอก ใช้เข้าสู่ระบบและรับอีเมล |
| รหัสผ่าน | บังคับกรอก ให้ Supabase Auth จัดการ ไม่เก็บเองในตารางข้อมูลสมาชิก |
| สถาบัน/หน่วยงาน | ไม่บังคับกรอก เลือกจาก Dropdown ที่ค้นหาชื่อได้ |
| ตัวเลือกอื่น ๆ | หากไม่มีสถาบันในรายการ ให้เลือกอื่น ๆ และพิมพ์ชื่อเอง |

Admin เพิ่ม แก้ไข และปิดใช้งานรายชื่อสถาบันใน CMS ได้
การพิมพ์ชื่อผ่านตัวเลือกอื่น ๆ ไม่ใช่การเพิ่มชื่อเข้ารายการกลางโดยอัตโนมัติ

## 3. ขั้นตอนอนุมัติและสถานะบัญชี

```text
สมัคร → ยืนยันอีเมล → รอ Admin พิจารณา
                         ├─ อนุมัติ → แจ้งอีเมล → ใช้ Education ได้ทุกหมวด
                         └─ ปฏิเสธพร้อมเหตุผล → แจ้งอีเมล
                                                ↓
                                   แก้ข้อมูลและส่งคำขอใหม่จากบัญชีเดิม
```

- การยืนยันอีเมลและการอนุมัติเป็นคนละเรื่อง ต้องเก็บและตรวจแยกกัน
- ต้องยืนยันอีเมลก่อนเข้าคิวให้ Admin พิจารณา
- เมื่อผู้สมัครยืนยันอีเมลและเข้าคิวรออนุมัติ ให้มีการแจ้งเตือนภายใน CMS และรายการรออนุมัติให้ Admin เข้ามาตรวจสอบ ไม่ส่งอีเมลแจ้ง Admin สำหรับเหตุการณ์นี้
- การตัดสินใจนี้ไม่เปลี่ยนอีเมลยืนยันตัวตนและอีเมลแจ้งผลอนุมัติ/ปฏิเสธที่ส่งให้ผู้สมัคร
- Admin ต้องระบุเหตุผลเมื่อปฏิเสธ และระบบส่งเหตุผลให้ผู้สมัครทางอีเมล
- ผู้ถูกปฏิเสธแก้ไขข้อมูลและส่งคำขอใหม่จากบัญชีเดิมได้
- เก็บประวัติการพิจารณาทุกครั้ง ไม่เขียนทับจนสูญเสียประวัติเดิม
- Admin ระงับและคืนสิทธิ์ผู้ที่ผ่านอนุมัติแล้วได้ โดยต้องระบุเหตุผลเมื่อระงับ
- ผู้ยังไม่ผ่านอนุมัติหรือถูกระงับต้องเข้าถึงเนื้อหาที่จำกัดสิทธิ์ไม่ได้

ชื่อสถานะที่เสนอสำหรับออกแบบฐานข้อมูล: `pending`, `approved`, `rejected`, `suspended`
สถานะยืนยันอีเมลให้ใช้ข้อมูลจาก Supabase Auth แยกจากสถานะอนุมัติ
รายละเอียดหน้ารอสถานะและการอนุญาต session ก่อนอนุมัติจะออกแบบในขั้น implementation โดยต้องไม่เปิดสิทธิ์เรียนก่อนอนุมัติ

## 4. บัญชี Admin

- Admin ทุกคนมีสิทธิ์เท่ากันในการจัดการสมาชิก สถาบัน และเนื้อหา
- Dev เป็นผู้จัดการการสร้างบัญชีและกำหนดสิทธิ์ Admin
- ไม่มีเมนูให้ Admin สร้างหรือเชิญ Admin เพิ่มเองใน CMS รุ่นแรก
- ขั้นตอนตั้งรหัสผ่าน กู้คืนบัญชี และการส่งมอบบัญชี Admin ให้กำหนดก่อนเปิดระบบจริง

## 5. ขอบเขต CMS รุ่นแรก

| หมวด | สิ่งที่จัดการ |
|---|---|
| สมาชิก | ตรวจผู้สมัคร อนุมัติ ปฏิเสธ ระงับ และคืนสิทธิ์ |
| สถาบัน/หน่วยงาน | เพิ่ม แก้ไข และปิดใช้งานตัวเลือก |
| Education | เพิ่ม แก้ไข ลบ และจัดลำดับบทเรียน/หัวข้อ พร้อมเนื้อหาแบบข้อความและรูปภาพ |
| EV Component Lab | ข้อความและรูปภาพอธิบายชิ้นส่วน |
| ประวัติ | ประวัติแก้ไข เผยแพร่ ย้อนเวอร์ชัน และการจัดการสมาชิก |

- ภาษาไทยเป็นหลัก พิมพ์ศัพท์เทคนิคภาษาอังกฤษร่วมในเนื้อหาได้ ไม่ทำฉบับแปลสองภาษาในระยะแรก
- สื่อในเนื้อหามีเฉพาะข้อความและรูปภาพ ไม่รวม PDF วิดีโอ หรือ YouTube
- Admin ไม่จัดการไฟล์ GLB หรือ config ของ Cutaway/Exploded ให้ Dev ดูแลในระยะแรก
- ยังไม่เปิดให้ CMS แก้ simulation logic, decoder หรือโค้ดของเว็บไซต์
- Admin จัดการบทเรียนและหัวข้อได้ครบ รวมถึงเพิ่ม แก้ไข ลบ และจัดลำดับ ไม่จำกัดเฉพาะช่องในโครงบทเรียนที่ Dev เตรียมไว้
- การเปลี่ยนโครงสร้างและลำดับบทเรียนต้องผ่าน Draft, Preview และ Publish เช่นเดียวกับการแก้เนื้อหา พร้อมเก็บ audit log และประวัติสำหรับย้อนเวอร์ชัน

## 6. การกรอกเนื้อหา

แนวทางที่เสนอเพื่อออกแบบฟอร์ม: Admin พิมพ์หรือก๊อปปี้วางลงในช่องที่ Dev เตรียมไว้ ไม่ต้องเตรียม JSON หรือแก้โค้ด

- ข้อความสั้นใช้ Input/Textarea เช่น ชื่อหัวข้อ คำอธิบาย และชื่อชิ้นส่วน
- เนื้อหายาวใช้เครื่องมือจัดข้อความที่จำกัดรูปแบบ เช่น หัวข้อ ตัวหนา รายการ และลิงก์
- ระบบควบคุมฟอนต์ สี และระยะห่าง รวมถึงล้างรูปแบบที่ไม่รองรับเมื่อวางข้อความจากเอกสารอื่น
- ไม่รับ HTML, JavaScript หรือ CSS ที่ Admin เขียนเอง
- รูปภาพให้อัปโหลดผ่าน CMS พร้อมช่องคำอธิบายภาพ
- ตรวจช่องบังคับ ขนาดข้อมูล และไฟล์ก่อนบันทึก/เผยแพร่
- รายการช่องจริง รูปแบบบทเรียน และเพดานขนาดรูปจะออกแบบเพิ่มเติม ไม่ถือว่าตัวอย่างช่องทั้งหมดได้รับอนุมัติแล้ว

## 7. Draft, Preview, Publish และการย้อนเวอร์ชัน

```text
บันทึกร่าง → ดูตัวอย่าง → เผยแพร่ → แสดงบน Education
```

- ระหว่างแก้ร่าง เว็บไซต์จริงยังแสดงเวอร์ชันที่เผยแพร่ล่าสุด
- เนื้อหาร่างและรูปที่ยังไม่เผยแพร่ต้องไม่รั่วไปยังหน้า Education ของอาจารย์
- Admin ดูตัวอย่างก่อนเผยแพร่ได้
- Admin ย้อนกลับไปใช้เวอร์ชันก่อนหน้าได้ พร้อมเก็บประวัติการย้อนกลับ
- การย้อนเวอร์ชันไม่ลบประวัติที่เกิดขึ้นแล้ว
- ข้อผิดพลาดของเนื้อหาใช้การแก้ร่าง/เผยแพร่หรือย้อนเวอร์ชัน
- ข้อผิดพลาดของระบบบน production ต้องแจ้ง Dev แก้ไข ไม่มีข้อตกลงว่าต้องสร้างระบบ ticket ภายใน CMS

## 8. Audit log

CMS ต้องเก็บ log การแก้ไขทุกครั้ง โดย Admin ลบ log ไม่ได้

ข้อมูลที่ต้องออกแบบให้ตรวจย้อนหลังได้:

- ผู้ทำรายการ วันเวลา ประเภทรายการ และข้อมูล/เวอร์ชันที่เกี่ยวข้อง
- การบันทึกแก้ไขเนื้อหา การเผยแพร่ และการย้อนเวอร์ชัน
- การอนุมัติ ปฏิเสธ ระงับ คืนสิทธิ์ และเหตุผลการพิจารณา
- การเพิ่ม แก้ไข หรือปิดใช้งานสถาบัน และการเปลี่ยนแปลงสื่อที่เกี่ยวข้อง
- ข้อมูลก่อน/หลัง หรือการอ้างอิงเวอร์ชันที่เพียงพอสำหรับตรวจสอบการเปลี่ยนแปลง

คำว่า “ทุกครั้ง” ใช้กับการบันทึกการเปลี่ยนแปลงที่สำเร็จ ไม่ใช่ทุกการกดแป้นพิมพ์
ไม่บันทึกรหัสผ่าน access token หรือ secret ลง log
ระยะเวลาเก็บ log ยังไม่ได้กำหนด

## 9. แนวทางเทคนิคที่เสนอ

ข้อตกลงการเตรียมระบบ: เจ้าของโปรเจกต์กำลังจะสร้าง Supabase Project ใหม่สำหรับงานนี้โดยเฉพาะ ยังไม่มีการเชื่อมต่อหรือเปลี่ยนฐานข้อมูลจริงในขั้นวางแผน

เป็นแนวทางสำหรับพัฒนาต่อ ไม่ใช่งานที่ทำเสร็จแล้ว:

- ข้อตกลงสถาปัตยกรรมล่าสุด: monorepo แยก React Education (`apps/education-web`), React Admin (`apps/admin-web`) และ NestJS/TypeScript API (`apps/api`) ตาม [ARCHITECTURE.md](ARCHITECTURE.md)
- เส้นทางตัวอย่างใน Education: `/login`, `/register`, `/pending-approval`, `/learn/*`; Admin เป็นแอปแยก ไม่ต้อง bundle เข้า Education
- Supabase Auth ดูแลบัญชี PostgreSQL ดูแลข้อมูล Storage ดูแลรูปภาพ
- ใช้ RLS ตรวจทั้งสิทธิ์และสถานะบัญชี ไม่อาศัยการซ่อนเมนูเพียงอย่างเดียว
- สมาชิกเปลี่ยน role หรืออนุมัติตัวเองไม่ได้
- NestJS จัดการ API กลาง การตรวจ JWT/สิทธิ์ และงานประสานอีเมล โดยคง transaction/RLS/audit ที่ฐานข้อมูล ไม่ทำกติกาซ้ำใน Edge Functions
- secret keys อยู่ฝั่ง Server เท่านั้น
- Schema, RLS และการเปลี่ยนแปลงฐานข้อมูลเก็บเป็น migrations ใน repo
- Simulation core และ decoder แยกจาก React และ Backend ตามโครงสร้างเดิม
- Backend เริ่มเป็น modular monolith บริการเดียว ยังไม่แยก microservices และไม่แยก repository ของ Admin

## 10. ลำดับงานที่เสนอ

1. สรุปกติกาที่เหลือ ออกแบบ schema และขอบเขตข้อมูลที่ Admin แก้ได้
2. Member & Access Foundation: migrations, RLS, Supabase client และขั้นตอนสร้าง Admin คนแรก
3. ระบบสมัคร ยืนยันอีเมล เข้าระบบ ลืมรหัสผ่าน และหน้าสถานะ
4. Admin จัดการสมาชิกและสถาบัน พร้อมอีเมลและ audit log
5. CMS Education: ฟอร์มข้อความ/รูป Draft, Preview, Publish และ rollback
6. ขยายรูปแบบ CMS ไป EV Component Lab

แต่ละช่วงเปิด feature branch อายุสั้นตามคู่มือ branch ไม่เปิดทุก branch ค้างพร้อมกัน
งาน export HTML, เอกสารข้อตกลง และ Supabase client แยก commit ตามขอบเขตก่อนเริ่ม branch งานสมาชิก เพื่อไม่ให้ปนกับการพัฒนาระบบสิทธิ์
เอกสารนี้ไม่ได้อนุญาตให้ Commit, Push, Deploy หรือเปลี่ยนฐานข้อมูลจริงโดยอัตโนมัติ

## 11. ประเด็นที่ยังไม่ได้ข้อสรุป

คำถามหลักด้านขอบเขตสำหรับรอบวางแผนนี้ได้ข้อสรุปแล้ว ใช้ Supabase Project ใหม่สำหรับโปรเจกต์นี้

เตรียม Project URL และ publishable key ใน `apps/education-web/.env.local` (ย้ายจาก root) พร้อม Supabase browser client แล้ว โดยไม่เก็บค่าจริงในเอกสาร
ข้อมูลสำหรับขั้นตั้งค่าที่ยังรอ: บริการ/โดเมนส่งอีเมล และ URL ของเว็บสำหรับ Auth redirects
ไม่ต้องส่ง database password, secret key หรือ service_role key ผ่านแชต ให้กำหนดผ่าน environment/secrets ในขั้นตั้งค่า

รายละเอียดทางเทคนิคที่จะกำหนดก่อน production: validation และขนาดรูป, ระยะเวลาเก็บ audit log,
การส่งอีเมลซ้ำเมื่อผิดพลาด, พฤติกรรมคืนสิทธิ์/ระงับสิทธิ์, การแจ้งอีเมลกรณีระงับ/คืนสิทธิ์,
และขั้นตอนทดสอบสิทธิ์สำคัญ ไม่ถือว่าได้รับคำตอบแล้วในเอกสารนี้
